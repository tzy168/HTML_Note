国内主流云平台项目部署手册

覆盖 阿里云 · 腾讯云 · 华为云 · 百度智能云 · 火山引擎，从零资源到稳定上线的完整操作路径。

适用对象：后端 / 前端 / 运维工程师 · 内容以“可直接照做”为准则 · 控制台界面可能随版本更新微调，菜单名以实际为准

如何使用本手册

第 1 章给出通用做法（在任何一家云上都成立），第 2 章给出各平台差异点（控制台入口、CLI、镜像仓库地址等）。如果你只部署一台机器上的 Web 服务，读完第 1 章即可开工；如果要上容器、流水线、多地域，再按目录跳读。

本手册不写具体价格：云产品价格随规格、地域、活动频繁变化，请以各平台官网价格计算器为准。

00手册总览

一次完整的部署，本质是七件事：把计算资源准备好、把网络通路打开、把运行时装好、把代码放上去、让进程稳定地跑、把流量接进来、然后看得见它的状态。国内五家主流平台在这七件事上的能力是同构的，差异主要体现在命名、控制台路径和周边生态。

三条常见路线，先选一条

A. 单机部署 最快

一台云服务器 + Nginx + systemd。适合管理后台、内部系统、日均万级以内访问、单体应用。上线最快，成本最低，运维心智负担小。

B. 容器化 / K8s 主流

镜像构建 → 推送到云上镜像仓库 → 部署到容器服务（ACK / TKE / CCE / VKE）。适合微服务、多实例、需要滚动更新与自动扩缩容。

C. Serverless / 托管 最省心

函数计算 + 对象存储静态托管 + API 网关。适合前端站点、轻量接口、定时任务、流量波峰波谷明显的场景。几乎不用管服务器。

选型建议

不要按“哪家便宜”选，优先看三件事：① 你的用户主要在哪个区域（就近选地域）；② 你已有的域名在哪家备案（接入商与备案主体一致最省事）；③ 团队熟悉哪个控制台。五家在国内主流地域的延迟差异，对绝大多数业务而言远小于架构与代码质量带来的差异。

02标准部署流程（一句话版）

  1. 开资源创建 VPC、安全组、密钥对，购买一台云服务器并绑定公网 IP。
  2. 连上去用 SSH 密钥登录，创建部署专用用户，禁止 root 直登。
  3. 装环境系统更新、安装运行时（Node / Java / Python / Go）、安装 Nginx。
  4. 传代码本地构建产物打包上传，或用 Git 拉取后在服务器构建，软链接切换版本。
  5. 跑起来配置 systemd 单元文件，设置开机自启与崩溃自动重启。
  6. 接流量Nginx 反向代理到应用端口，配置域名解析与免费 HTTPS 证书。
  7. 看得见安装云监控插件，配置 CPU / 内存 / 磁盘 / 端口告警联系人。

03部署前置清单

开工前把下面这些确认完，能避免 80% 的返工。

  • 已确定部署地域（建议与用户群就近，备案必须在大陆地域；港澳台及海外地域无需备案）
  • 已确定规格：CPU / 内存 / 系统盘 / 带宽峰值，并预留 30% 余量
  • 已确定操作系统（推荐 Alibaba Cloud Linux / TencentOS / Ubuntu LTS / AlmaLinux，避免即将 EOL 的版本）
  • 已创建SSH 密钥对并妥善保存私钥（.pem 仅此一次下载机会）
  • 已规划端口清单：22（SSH）、80、443、以及应用端口（默认只内网暴露）
  • 已准备域名并确认是否已完成 ICP 备案
  • 已准备代码仓库地址与部署所需的环境变量、密钥（不要写进代码库）
  • 已确认数据存放位置：数据库用云托管还是自建，文件是否上对象存储
  • 已确认回滚方案：上一版本产物是否保留，数据库变更是否可逆

账号与权限

绝对不要用主账号的 AccessKey 做日常部署。正确做法是创建子用户 / 角色，按需授予最小权限。

平台子账号体系建议做法
阿里云RAM 用户 / RAM 角色为 CI 创建 RAM 用户，仅授予容器镜像服务与 ECS 的指定权限；服务器用实例 RAM 角色免密钥访问 OSS
腾讯云CAM 子账号 / 角色子账号仅授予 QcloudCVMFullAccess 等必要策略，开启 MFA；COS 用临时密钥 STS 访问
华为云IAM 用户 / 委托按项目分组授权，跨账号场景用委托（Agency）
百度智能云IAM 用户 / 角色按最小权限原则分配策略，开启操作审计
火山引擎IAM 用户 / 角色为流水线创建专用 IAM 用户并定期轮换密钥
密钥安全红线

AccessKey 一旦提交进 Git 仓库，请立即禁用并轮换，不要心存侥幸——公开仓库的密钥扫描机器人通常在几分钟内就会找上门。生产环境优先使用实例角色 / 临时凭证，从源头消除长期密钥。

网络与安全组规划

安全组是云上的虚拟防火墙，是有状态的：放行入方向后，出方向响应自动放行。

方向协议端口来源说明
入22 / TCP公司或家庭固定 IP/32不要对 0.0.0.0/0 开放；无公网 IP 时用云上堡垒机或 VPN 接入
入80 / TCP0.0.0.0/0HTTP，通常配置为 301 跳转 HTTPS
入443 / TCP0.0.0.0/0HTTPS
入应用端口（如 3000）仅负载均衡安全组 / 内网网段应用端口不应对公网开放，由 Nginx 或 CLB 转发
出全部0.0.0.0/0默认允许；合规场景可收紧为白名单
经验值

至少准备两个安全组：一个 sg-web（80/443 对公网），一个 sg-internal（只对内网网段开放数据库、Redis、应用端口）。Web 层与数据层用不同安全组，是性价比最高的安全投入。

域名与 ICP 备案

  • 服务器在中国大陆地域，域名必须完成 ICP 备案才能通过 80/443 对外提供服务；港澳台及海外地域不需要。
  • 备案在服务接入商处提交（阿里云备案、腾讯云备案、华为云备案等），由各省通信管理局审核，通常需 1–20 个工作日，各省管局时效不同。
  • 备案需：真实身份信息、域名证书、网站负责人核验（多数平台用 App 人脸核验）、服务器（或服务码）在对应平台。
  • 网站开通后 30 日内需完成公安备案（全国互联网安全管理服务平台）。
  • 提前规划：如果上线时间紧，建议先备案再开发收尾，备案是整个链路里唯一无法靠加人加速的环节。

一云服务器部署（通用做法）

这一章的流程在任意一家云上都适用，只在控制台入口上有差别。

3.1 系统初始化

bash — 首次登录后必做
# 1) 更新系统
sudo apt update && sudo apt upgrade -y          # Ubuntu / Debian
# sudo dnf update -y                            # AlmaLinux / Rocky / TencentOS / OpenCloudOS
# sudo yum update -y                            # CentOS 7

# 2) 设置主机名与时区
sudo hostnamectl set-hostname web-prod-01
sudo timedatectl set-timezone Asia/Shanghai

# 3) 创建部署用户（不要直接用 root 跑应用）
sudo useradd -m -s /bin/bash deploy
sudo passwd -l deploy            # 锁定密码登录，只允许密钥
sudo mkdir -p /home/deploy/.ssh
sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh
sudo chmod 600 /home/deploy/.ssh/authorized_keys
echo "deploy ALL=(ALL) NOPASSWD:ALL" | sudo tee /etc/sudoers.d/deploy

# 4) 加固 SSH（改完先别断开，另开一个窗口验证能登录再关当前连接）
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl restart sshd

# 5) 防火墙
sudo ufw allow 22/tcp; sudo ufw allow 80/tcp; sudo ufw allow 443/tcp; sudo ufw enable   # Ubuntu
# sudo firewall-cmd --permanent --add-service={ssh,http,https} && sudo firewall-cmd --reload  # RHEL 系

# 6) 应用目录
sudo mkdir -p /opt/app /var/log/app
sudo chown -R deploy:deploy /opt/app /var/log/app
操作顺序警告

修改 sshd_config 后务必：sudo sshd -t 校验语法 → 新开一个终端窗口测试能否登录 → 确认无误后再关闭原连接。顺序反了，你就会被锁在服务器外面，只能去控制台 VNC 救援。

3.3 代码发布：目录约定与零停机切换

推荐的目录结构，支持秒级回滚：

目录约定
/opt/app/
├── releases/
│   ├── 2026-09-09-1015/      # 每次发布一个新目录（不可变）
│   └── 2026-09-01-0930/      # 保留最近 5 个版本用于回滚
├── shared/
│   ├── .env                  # 环境变量，不进 Git
│   └── uploads/              # 用户上传文件（建议改用对象存储）
└── current -> releases/2026-09-09-1015/   # 软链接，指向当前版本
bash — 发布脚本 deploy.sh
#!/usr/bin/env bash
set -euo pipefail
APP_DIR=/opt/app
KEEP=5

# 用法：./deploy.sh dist.tar.gz
TARBAL=$(readlink -f "$1")
STAMP=$(date +%F-%H%M)
REL=$APP_DIR/releases/$STAMP

mkdir -p "$REL"
tar -xzf "$TARBAL" -C "$REL"
ln -sfn "$APP_DIR/shared/.env" "$REL/.env"

# 安装依赖（Node 示例）
cd "$REL" && pnpm install --prod --frozen-lockfile

# 原子切换
ln -sfn "$REL" "$APP_DIR/current.tmp"
mv -Tf "$APP_DIR/current.tmp" "$APP_DIR/current"

# 重启服务
sudo systemctl restart myapp
sleep 3
systemctl is-active --quiet myapp && echo "deploy OK: $STAMP" || { echo "FAILED"; exit 1; }

# 清理旧版本
cd "$APP_DIR/releases" && ls -1t | tail -n +$((KEEP+1)) | xargs -r rm -rf
为什么用软链接

切换版本只有 mv -Tf 一次原子操作，中间不存在“半个新版本”的状态。回滚就是把软链接指回上一个目录再重启，通常 5 秒内完成。

3.5 Nginx 反向代理

/etc/nginx/conf.d/myapp.conf
upstream myapp {
    server 127.0.0.1:3000;
    keepalive 32;
}

server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/nginx/cert/example.com.pem;
    ssl_certificate_key /etc/nginx/cert/example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;

    client_max_body_size 20m;
    gzip on;
    gzip_types text/plain text/css application/json application/javascript;

    access_log /var/log/nginx/myapp.access.log;
    error_log  /var/log/nginx/myapp.error.log;

    # 前端静态资源
    location /assets/ {
        root /opt/app/current/public;
        expires 7d;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://myapp;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }

    # 单页应用路由回退
    location / {
        root /opt/app/current/public;
        try_files $uri $uri/ /index.html;
    }
}

sudo systemctl reload nginx   # 平滑重载，不断连接
sudo systemctl enable nginx

3.6 HTTPS 证书

两种方案，按场景选：

方案适用优点注意
云平台免费 DV 证书 + 负载均衡 / CDN 托管单域名、推荐自动续期、免运维、可挂 CDN各平台免费额度与有效期不同，以控制台为准；不支持通配符
Let's Encrypt + certbot需要通配符、多域名、自建 Nginx免费、支持泛域名（需 DNS 验证）90 天有效期，必须配置自动续期

3.1 写好 Dockerfile

Dockerfile — Node 服务多阶段构建示例
# ---------- 构建阶段 ----------
FROM node:20-alpine AS builder
WORKDIR /src
COPY package.json pnpm-lock.yaml ./
RUN npm i -g pnpm && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build

# ---------- 运行阶段 ----------
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /src/package.json ./
COPY --from=builder /src/node_modules ./node_modules
COPY --from=builder /src/dist ./dist

USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://127.0.0.1:3000/healthz || exit 1
CMD ["node", "dist/server.js"]
Dockerfile 五条硬规则

① 用多阶段构建，运行镜像里不要有编译器和源码；② 依赖清单单独 COPY，充分利用构建缓存；③ 用 .dockerignore 排除 node_modules、.git、.env；④ 不要以 root 运行；⑤ 配置 HEALTHCHECK，让编排系统能真正判断存活。

三个最容易踩的坑

① 没配 readinessProbe：滚动更新时新 Pod 还没就绪就被摘掉旧 Pod，导致短暂 502；② 没配 preStop：Pod 直接退出，正在处理的请求被中断；③ 没设 resources.limits：单个 Pod 内存泄漏会拖垮整个节点。

所有敏感信息走仓库 Secrets 或云平台凭据管理（KMS / 凭据管家），不要把 .env 打进镜像，也不要在日志里打印环境变量。更进一步，用 OIDC 角色扮演 让流水线获取临时凭证，彻底不存长期密钥。

记录类型用途示例

七监控、日志与告警

7.1 必须配置的告警项

类别指标 / 检查建议阈值
主机CPU 使用率持续 5 分钟 > 80%
主机内存使用率持续 5 分钟 > 85%
主机磁盘使用率> 85%（留足日志增长空间）
网络公网出带宽、连接数接近上限 80%

证书HTTPS 证书剩余有效期< 15 天
业务关键接口 P95 耗时、错误率按业务基线设定
告警的三个原则

① 告警必须可行动——收到后不知道要做什么的告警，等于噪音，应该删掉或降级为看板指标；② 区分等级——电话/短信只给真正影响用户的问题，其余走企微/钉钉/邮件；③ 每个人都要能收到——告警只发给一个人，他休假时就是黑洞。

7.2 日志

  • 应用日志统一输出到 stdout/stderr，容器场景由运行时采集；非容器场景写入固定目录并配置轮转。
  • 日志务必带 requestId / traceId，否则线上排障只能靠猜。
  • 用 logrotate 或 Docker 的 log-opts 限制日志大小，避免日志把磁盘写满导致宕机（这是最常见的线上事故之一）。
  • 敏感信息脱敏：手机号、身份证、token 不应明文落盘。

八安全加固

  1. 最小权限：子账号 + 角色授权，禁止共享主账号；开启 MFA；定期轮换 AccessKey。
  2. 网络收敛：SSH 仅对固定 IP 或堡垒机开放；数据库、Redis 绝不对 0.0.0.0/0 开放。
  3. 主机加固：禁用密码登录与 root 登录；开启自动安全更新；安装主机安全 agent（各云都有免费基础版）。
  4. 应用防护：接入 WAF（可先开通基础防护）；接口做鉴权、限流、参数校验；管理后台加二次验证。
  5. 数据安全：启用云盘自动快照策略（例如每日 1 次、保留 7 天）；数据库开启备份并定期做恢复演练——没验证过的备份不算备份。
  6. 传输加密：全站 HTTPS，开启 HSTS；内网服务间调用也尽量用 TLS。
  7. 依赖与镜像：流水线中加入依赖漏洞扫描与镜像扫描；基础镜像定期更新。
  8. 审计：开启操作审计（ActionTrail / 云审计 / CTS 等），关键操作可追溯。

九成本优化

手段适用说明
包年包月长期稳定的基础负载相比按量付费有明显折扣；锁定 1 年或 3 年

第一件事：开预算告警

在任何优化之前，先在费用中心设置预算阈值告警（如达到月度预算的 80% 时通知）。成本事故和线上事故一样，都是发现得越晚损失越大。

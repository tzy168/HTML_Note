Redux / MobX / Zustand / Dva
同一件事的四种解法

四个库解决的是同一个问题：谁持有状态、谁修改状态、状态变了谁重渲染。 差别只在"约束"和"样板代码"的比例 —— 约束越多越可预测，样板越少越自由。 这份速查给出可直接粘贴的最小可用代码，以及选型时真正起作用的判断维度。

01 / Mind model

一句话心智模型

先记住这一句，代码细节都是它的展开。

Redux

单一数据源 + 显式不可变更新

全局一棵状态树，改状态必须 dispatch(action)，由纯函数 reducer 算出新 state。

  • 状态是"快照"，可回放
  • 数据流单向且可追踪
  • 样板代码靠 RTK 大幅压缩

MobX

响应式 + 可变即更新

把对象变成 observable，直接赋值即可；谁读了谁就被自动追踪依赖，精准更新。

  • 像写普通对象一样写状态
  • 自动依赖收集，无需手写选择器
  • 细粒度到字段级重渲染

Zustand

极简 store + hooks 订阅

一个 create() 就是 store，组件用选择器订阅需要的那一小块，set 即更新。

  • 不需要 Provider 包裹
  • React 之外也能读写
  • 心智负担最低

Dva

约定式 model + saga 副作用

redux + redux-saga 的框架化封装，按 namespace/state/reducers/effects 约定组织。

  • 异步用 generator，可读性好
  • 与 umi / antd-pro 深度集成
  • 约定大于配置

04 / Usage

用法详解

同一个需求（计数器 + 异步拉取用户）的四种写法，左边定义状态，右边在组件里消费。

store/counterSlice.js
import { configureStore, createSlice, createAsyncThunk } from '@reduxjs/toolkit'

// 异步 thunk：自动产出 pending / fulfilled / rejected 三个 action
export const fetchUser = createAsyncThunk('counter/fetchUser', async (id) => {
  const res = await fetch(`/api/users/${id}`)
  return res.json()
})

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0, user: null, loading: false },
  reducers: {
    increment: (state) => { state.value += 1 },            // 内部 Immer，可"直接改"
    addBy: (state, action) => { state.value += action.payload },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUser.pending, (state) => { state.loading = true })
      .addCase(fetchUser.fulfilled, (state, action) => {
        state.loading = false
        state.user = action.payload
      })
  },
})

export const { increment, addBy } = counterSlice.actions
export const selectValue = (state) => state.counter.value

export const store = configureStore({
  reducer: { counter: counterSlice.reducer },
})
components/Counter.jsx
import { useSelector, useDispatch } from 'react-redux'
import { increment, addBy, fetchUser, selectValue } from '../store/counterSlice'

function Counter() {
  const value = useSelector(selectValue)
  const loading = useSelector((s) => s.counter.loading)
  const dispatch = useDispatch()

  return (
    <div>
      <span>{value}</span>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(addBy(5))}>+5</button>
      <button onClick={() => dispatch(fetchUser(1))}>
        {loading ? '加载中' : '拉取用户'}
      </button>
    </div>
  )
}
main.jsx — 入口注入 Provider
import { Provider } from 'react-redux'
import { store } from './store/counterSlice'

createRoot(document.getElementById('root')).render(
  <Provider store={store}>
    <Counter />
  </Provider>
)

要点与常见坑

  • 只在 createSlice 里可以"直接改" state，那是 Immer 的草稿；reducer 之外必须保持不可变。
  • useSelector 返回新对象/新数组会每次重渲染，多个值要么拆成多个 selector，要么配合 shallowEqual / createSelector。
  • 纯请求场景优先 RTK Query，自己写 loading / error / 缓存通常是在重复造轮子。
  • 不要在 reducer 里做副作用（请求、随机数、Date.now），它们必须保持纯函数。
stores/CounterStore.js
import { makeAutoObservable, runInAction, configure } from 'mobx'

configure({ enforceActions: 'observed' })   // 禁止在 action 外乱改状态

class CounterStore {
  value = 0
  user = null
  loading = false

  constructor() {
    makeAutoObservable(this)   // 字段→observable, getter→computed, 方法→action
  }

  get double() {                // computed：按依赖自动缓存
    return this.value * 2
  }

  increment() { this.value += 1 }
  addBy(n) { this.value += n }

  async fetchUser(id) {
    this.loading = true
    const data = await fetch(`/api/users/${id}`).then((r) => r.json())
    runInAction(() => {         // await 之后的修改必须包起来
      this.user = data
      this.loading = false
    })
  }
}

export const counterStore = new CounterStore()
components/Counter.jsx
import { observer } from 'mobx-react-lite'
import { counterStore } from '../stores/CounterStore'

// observer 追踪"渲染期间读过的" observable，变了才重渲染
const Counter = observer(() => (
  <div>
    <span>{counterStore.value} / {counterStore.double}</span>
    <button onClick={() => counterStore.increment()}>+1</button>
    <button onClick={() => counterStore.addBy(5)}>+5</button>
    <button onClick={() => counterStore.fetchUser(1)}>拉取用户</button>
  </div>
))
多 Store 用 Context 注入（可选）
import { createContext, useContext } from 'react'
import { useLocalObservable } from 'mobx-react-lite'

const StoreContext = createContext(null)
export const StoreProvider = StoreContext.Provider
export const useStore = () => useContext(StoreContext)

// 组件内局部状态也能响应式：
const local = useLocalObservable(() => ({ count: 0, inc() { this.count++ } }))

要点与常见坑

  • 忘记 observer 是最常见问题：组件不会响应更新，且没有任何报错。
  • 异步 await 之后的赋值必须放进 runInAction，否则触发严格模式警告。
  • 解构会切断响应式：先解构再渲染，组件就订阅不到变化了，直接 store.xxx 读取最稳。
  • TS 下用类字段需要把 useDefineForClassFields 设为 false，否则字段覆盖 observable。
  • computed 里别做副作用；它不是"会在变化时执行"，而是"被读取时才计算"。
store/useCounter.js
import { create } from 'zustand'
import { persist, devtools, subscribeWithSelector } from 'zustand/middleware'

// TS 推荐柯里化写法：create<State>()(middleware(...))
export const useCounter = create((set, get) => ({
  value: 0,
  user: null,

  // 返回"部分状态"，与旧值浅合并
  increment: () => set((s) => ({ value: s.value + 1 })),
  addBy: (n) => set((s) => ({ value: s.value + n })),
  reset: () => set({ value: 0, user: null }),

  // 异步就是普通 async 函数，随时 set
  fetchUser: async (id) => {
    const data = await fetch(`/api/users/${id}`).then((r) => r.json())
    set({ user: data })
  },
}))

// 加中间件：持久化 + devtools + 精确订阅
export const useCart = create(
  devtools(
    persist(
      (set) => ({ items: [], add: (i) => set((s) => ({ items: [...s.items, i] })) }),
      { name: 'cart-storage' }
    )
  )
)
components/Counter.jsx
import { useShallow } from 'zustand/react/shallow'
import { useCounter } from '../store/useCounter'

function Counter() {
  // 按需订阅：selector 的返回值就是重渲染的触发条件
  const value = useCounter((s) => s.value)
  const increment = useCounter((s) => s.increment)

  // 一次取多个值，用 useShallow 避免每次返回新对象导致重渲染
  const { user, reset } = useCounter(
    useShallow((s) => ({ user: s.user, reset: s.reset }))
  )

  return <button onClick={increment}>{value}</button>
}
React 之外读写 + 派生状态
// 在普通函数 / 事件监听 / 请求拦截器里直接用
useCounter.getState().value
useCounter.setState({ value: 10 })
const unsub = useCounter.subscribe((s) => console.log(s.value))

// 派生值不要存进 store，用 selector 算
const double = useCounter((s) => s.value * 2)

// 跨请求共享：直接把 fetch 结果 set 进去即可，无需 dispatch

要点与常见坑

  • v5 起 selector 返回新对象会无限重渲染警告，多值一定用 useShallow。
  • action 和 state 放在同一个对象里即可，不需要区分 reducer / action creator。
  • set 默认是浅合并；要替换整个状态用 set(x, true)。
  • 嵌套对象更新要手动展开（或配 immer 中间件），不会自动深层合并。
  • persist 在 SSR / Next.js 上要注意 hydration，首次渲染服务端拿不到 localStorage。
models/counter.js
const delay = (ms) => new Promise((r) => setTimeout(r, ms))

export default {
  namespace: 'counter',           // 全局唯一，也是 state 挂在 store 上的 key
  state: { value: 0, user: null },

  reducers: {                     // 同步：纯函数，必须返回新 state
    add(state, { payload }) {
      return { ...state, value: state.value + payload }
    },
    saveUser(state, { payload }) {
      return { ...state, user: payload }
    },
  },

  effects: {                      // 异步：generator + redux-saga
    *addDelay({ payload }, { call, put, select }) {
      yield call(delay, 1000)
      const value = yield select((s) => s.counter.value)
      yield put({ type: 'add', payload: value + payload })   // 可省略 namespace
    },
    *fetchUser({ payload }, { call, put }) {
      const data = yield call(fetchUserApi, payload)
      yield put({ type: 'saveUser', payload: data })
    },
  },

  subscriptions: {                // 订阅路由 / 键盘 / websocket 等外部源
    setup({ dispatch, history }) {
      return history.listen(({ pathname }) => {
        if (pathname === '/') dispatch({ type: 'fetchUser', payload: 1 })
      })
    },
  },
}

components/Counter.jsx
import { connect } from 'dva'      // umi 项目：import { connect } from 'umi'

function Counter({ value, loading, dispatch }) {
  return (
    <div>
      <span>{value}</span>
      <button onClick={() => dispatch({ type: 'counter/add', payload: 1 })}>+1</button>
      <button onClick={() => dispatch({ type: 'counter/fetchUser', payload: 1 })}>
        {loading ? '加载中' : '拉取用户'}
      </button>
    </div>
  )
}

export default connect(({ counter, loading }) => ({
  value: counter.value,
  loading: loading.effects['counter/fetchUser'],
}))(Counter)

要点与常见坑

  • reducers 必须返回新对象，直接改 state 不会触发更新（没有 Immer）。
  • effects 内部 yield put({ type: 'add' }) 省略 namespace 表示当前 model，跨 model 必须写全 'other/xxx'。
  • namespace 冲突会静默覆盖，中大型项目建议加前缀规范。
  • dva 本质是 redux + redux-saga 的封装，底层概念仍通用；新项目启动前建议评估维护活跃度。
  • dva-loading 几乎必装，否则要为每个请求手写 loading 字段。
05 / Decision

怎么选

回答三个问题，得到一个倾向性建议。权重是主观的，用来收敛讨论，不是判决书。

1. 项目规模与协作方式？
2. 团队更接受哪种写法？
3. 现有技术栈？
选择上面的选项后显示建议
未选择时，默认推荐：Zustand —— 新项目的低风险起点，迁移成本也最低。

迁移成本参考

Dva → Redux Toolkit / Zustand：model 结构天然对应，effects 改成 async 函数即可，成本可控。

MobX → Zustand：响应式心智需换成 selector 订阅，UI 层改动较多但逻辑基本可平移。

Zustand → Redux：通常在团队规模上升、需要审计与中间件时发生，方向相反的情况很少见。

一句话结论

  • 新项目、没特殊诉求 → Zustand
  • 多人协作 + 强可追溯 + 复杂数据获取 → Redux Toolkit
  • 领域模型复杂、追求字段级精准更新 → MobX
  • 维护 umi / antd-pro 老项目 → 继续用 Dva，新模块不必再新增

还有一个常被忽略的选项：先别上全局状态。Server 数据用 TanStack Query / SWR，URL 状态用路由参数，剩下的才是真正需要状态库的。

06 / Pitfalls

跨库通用坑

把服务端数据塞进状态库

请求缓存、失效、重试、去重，这些是数据获取库的活。状态库只放"客户端状态"（UI 开关、草稿、跨页共享的少量业务态）。

选择器返回新对象

Redux / Zustand / Dva 都用引用比较，selector 里写 { a, b } 或 map/filter 会每次产生新引用，导致无意义重渲染。

状态放得太深或太散

嵌套过深导致更新和订阅都变复杂；拆得过多又变成跨 store 互相引用。按"页面/领域"切分，通常比按技术类型切分更好维护。

忽略 SSR 与持久化

persist 在服务端渲染时读不到本地存储，容易 hydration 不一致；需要跳过首帧或延后恢复状态。

四个库的 API 以官方文档为准：Redux Toolkit、MobX、Zustand、Dva（dva 2.x / umi 插件）。本页示例为最小可运行骨架，按项目实际结构调整目录即可。

1CI/CD 基础概览

CI/CD 是一种软件工程实践：通过自动化流水线，把代码从「开发者本机」安全、快速、可重复地送到「生产环境」。

1
Commit

开发者提交代码到 Git 仓库（GitLab / GitHub / Gitee）。

2
Trigger

推送事件触发流水线（Webhook / 定时 / 手动）。

3
Build

拉取依赖、编译打包，产出可部署产物（jar / dist / 镜像）。

4
Test

单元测试、代码扫描、安全检测，质量门禁拦截问题。

5
Deploy

部署到测试 / 预发 / 生产环境，支持灰度与回滚。

持续集成 CI

频繁（每天多次）将代码集成到主干，每次集成都自动构建 + 自动测试，尽早发现集成错误。

持续交付 CD

保证代码随时处于「可发布」状态，产物已构建待命，上线由人工一键触发。

持续部署 CD

在持续交付基础上更进一步：通过全部质量门禁后，自动发布到生产环境，无人工介入。

为什么需要它？ 手工打包部署的典型痛点：环境不一致（"我这里能跑"）、漏测漏步骤、发布窗口长、出问题无法快速回滚。CI/CD 用「流水线即代码」把发布过程固化下来，让发布从"仪式"变成"日常"。

2什么是 Jenkins / GitLab CI/CD

Jenkins

开源、自托管的自动化服务器，2011 年从 Hudson 分叉而来，是目前生态最庞大的 CI/CD 工具。核心特点是插件化（1800+ 插件）与Pipeline as Code（Jenkinsfile）。它不绑定任何代码托管平台，可以和 GitLab、GitHub、SVN、Bitbucket 任意组合。

GitLab CI/CD

GitLab 平台内置的 CI/CD 引擎，与代码仓库、Merge Request、镜像仓库、Issue 深度集成。只需在仓库根目录放一个 .gitlab-ci.yml，由 GitLab Runner 负责执行任务。开箱即用，配置成本极低。

一句话区分：Jenkins 是"通用自动化引擎"，什么都能做、什么都要自己配；GitLab CI/CD 是"仓库原生流水线"，专注、简洁，但强依赖 GitLab 生态。

3Jenkins 介绍

Jenkins 用 Java 编写，以 Controller（主控）+ Agent（执行节点）的分布式架构运行，通过插件连接几乎一切工具链。

核心概念

Job / Item

一次可执行的任务定义。Freestyle（界面配置）或 Pipeline（代码定义）是最常见的两种类型。

Pipeline

由多个 Stage 组成的流水线。Declarative（声明式，推荐）与 Scripted（脚本式 Groovy）两种语法。

Stage / Step

Stage 是逻辑阶段（构建、测试、部署）；Step 是最小执行单元（sh、checkout、archiveArtifacts）。

Node / Agent

Agent 指定任务在哪台机器或容器里跑（any / label / docker / kubernetes）。

Executor

每个节点可并行执行的任务槽位数量，决定了并发能力。

Workspace

单次构建在节点上的工作目录，存放检出的源码与中间产物。

Plugin

能力的来源：Git、Credentials、Docker、Kubernetes、Blue Ocean、SonarQube 等。

Credentials

集中管理 SSH 私钥、用户名密码、Token、Kubeconfig，流水线通过 ID 引用，不落明文。

Artifact / Fingerprint

归档构建产物（jar、dist 包）并记录指纹，便于追溯与下游引用。

架构与工作原理

Controller
负责调度构建、保存配置与历史、提供 Web UI 和 API。本身不推荐直接跑构建任务。
Agent
通过 SSH、JNLP 或 Kubernetes Pod 接入，真正执行构建。可按标签（label）分组，如 linux、docker、macos。
Jenkinsfile
声明式流水线脚本，随代码一起版本管理（Pipeline as Code），支持 Code Review。
触发链路
Git push → Webhook（或 SCM 轮询）→ Controller 排队 → 分配空闲 Agent → 执行 Stage → 归档产物 / 通知。

优势与局限

优势

  • 生态最全：1800+ 插件，几乎能接入任何系统。
  • 与代码平台解耦，GitLab / GitHub / SVN 通吃。
  • 分布式扩展成熟，支持动态 Kubernetes Agent，弹性伸缩。
  • 完全自托管，数据与网络全在内网，合规友好。
  • 社区资料丰富，遇到问题基本都能搜到答案。

局限

  • 插件质量参差，升级易踩兼容性坑，需谨慎管理。
  • UI 偏传统，学习曲线对新人略陡。
  • 需要自行维护服务器、备份、权限体系与高可用。
  • Groovy 沙箱与脚本审批增加一定运维负担。

4GitLab CI/CD 介绍

GitLab CI/CD 由 GitLab 实例（负责编排）+ GitLab Runner（负责执行）两部分组成，配置全部集中在仓库根目录的 .gitlab-ci.yml。

核心概念

Pipeline

一次 CI 运行的顶层容器，由 Stages 组成。每次 push / MR 会生成一条流水线。

Stage

阶段（build / test / deploy）。同一 Stage 内的 Job 并行，Stage 之间串行。

Job

最小执行单元，包含 script 命令、运行环境（image）、产物与规则。

Runner

执行 Job 的代理程序，支持 Shell、Docker、Kubernetes 等 executor，可打 Tag 分组调度。

.gitlab-ci.yml

流水线定义文件，YAML 语法，随代码版本管理，支持 include 模板复用。

Artifacts / Cache

Artifacts 在 Job 之间传递产物并支持下载；Cache 用于缓存依赖（node_modules、.m2）加速构建。

Variables

预定义变量（CI_COMMIT_SHA 等）与自定义变量，支持 masked（脱敏）与 protected（仅保护分支）。

Environment

记录部署目标（staging / production），支持查看部署历史与一键回滚。

rules / only

控制 Job 何时运行，如仅在 main 分支、仅在 MR、仅当文件变更时。

架构与工作原理

调度流程
git push → GitLab 解析 .gitlab-ci.yml → 生成 Pipeline → 按 Tag 匹配在线 Runner → Runner 领取 Job → 上报日志与产物 → 更新 MR 里的结果徽标。
Executor
Shell（直接跑在宿主机，简单但隔离差）、Docker（每个 Job 独立容器，推荐）、Kubernetes（弹性 Pod，适合大规模）。
内置集成
Container Registry、Package Registry、Release、Review Apps、Merge Request 质量报告、SAST/DAST 安全扫描。

优势与局限

优势

  • 与 GitLab 仓库、MR、Issue 天然打通，无需额外插件。
  • 一个 YAML 文件搞定全部，学习成本极低，新人 30 分钟上手。
  • 内置镜像仓库与制品仓库，DevOps 闭环完整。
  • MR 页面直接看流水线结果、测试报告、覆盖率。
  • 托管版（gitlab.com）零运维，自托管版也有官方 Runner。

局限

  • 强绑定 GitLab，跨平台（GitHub / 多平台混合）场景不适用。
  • 复杂编排能力弱于 Jenkins（如跨项目复杂人工审批流）。
  • UI 配置能力弱，重度依赖写 YAML。
  • Runner 的机器资源与网络安全需自行规划。

维度JenkinsGitLab CI/CD

6Jenkins 操作手册

下面以 Linux + Docker 部署为例，从零搭建一套可跑 Java / Node 项目的流水线。

6.1 安装与初始化

方式 A：Docker 部署（推荐）

bash · docker 部署 Jenkins LTS
# 1. 创建持久化目录
mkdir -p /opt/jenkins/home && chown -R 1000:1000 /opt/jenkins/home

# 2. 启动容器（映射 8080 控制台 / 50000 Agent 通信端口）
docker run -d --name jenkins --restart=unless-stopped \
  -p 8080:8080 -p 50000:50000 \
  -v /opt/jenkins/home:/var/jenkins_home \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /usr/bin/docker:/usr/bin/docker \
  jenkins/jenkins:lts-jdk17

# 3. 查看初始管理员密码
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

方式 B：裸机 war 包部署

bash · 直接运行 war 包
# 需先安装 JDK 17
java -jar jenkins.war --httpPort=8080
# 生产建议配置为 systemd 服务，设置 JENKINS_HOME 与堆内存参数
  1. 浏览器访问 http://<服务器IP>:8080，输入上一步获取的初始密码。
  2. 插件安装页选择 「安装推荐的插件」（Git、Pipeline、Credentials、Workspace Cleanup 等）。
  3. 创建管理员账号，确认 Jenkins URL（后续 Git Webhook 会用到，务必填对）。
  4. 进入 Manage Jenkins → System，核对 Jenkins Location 中的 URL；进入 Tools 配置 JDK / Git / Maven / NodeJS 路径。
常用插件清单：Pipeline、Git、Credentials Binding、SSH Agent、Docker Pipeline、Kubernetes、Blue Ocean、Generic Webhook Trigger、DingTalk / 企业微信通知、SonarQube Scanner。

6.2 凭据与工具配置

  1. Manage Jenkins → Credentials → System → Global credentials → Add Credentials。
  2. 拉 Git 代码：类型选 SSH Username with private key，粘贴私钥；或 Username with password（GitLab 可用 Access Token 作为密码）。
  3. 推镜像 / 部署：类型选 Secret text 存 Token，或 Secret file 上传 Kubeconfig。
  4. 记住填写的 ID（如 gitlab-ssh-key），Jenkinsfile 中通过 credentialsId 引用。
groovy · 在流水线中使用凭据（不落明文）
environment {
  REGISTRY_CRED = credentials('harbor-robot-account')   // 自动拆分为 _USR / _PSW
  KUBECONFIG    = credentials('prod-kubeconfig')         // Secret file，映射为临时文件路径
}
steps {
  sh 'echo $REGISTRY_CRED_PSW | docker login registry.example.com -u $REGISTRY_CRED_USR --password-stdin'
}

6.3 创建第一个 Pipeline

  1. 首页 → 新建任务（New Item） → 输入名称 → 选择 流水线（Pipeline） → 确定。
  2. 在 Pipeline 区块，Definition 选择 Pipeline script from SCM，SCM 选 Git。
  3. 填写仓库 URL、选择上一步创建的凭据、指定分支（如 */main）。
  4. Script Path 填 Jenkinsfile（默认即可，即读取仓库根目录的 Jenkinsfile）。
  5. 保存后点击 立即构建（Build Now），在 Stage View / Blue Ocean 中查看执行过程与日志。
为什么要用 Jenkinsfile？把流水线定义写进代码仓库后，它就能被 Code Review、被版本回滚、随分支走（不同分支可有不同的发布逻辑），这是 Jenkins 使用方式的核心最佳实践。

6.4 Jenkinsfile 实战（可直接改造使用）

Jenkinsfile · Declarative Pipeline 完整示例
pipeline {
    agent any                                  // 也可：agent { label 'docker' }

    options {
        timestamps()
        timeout(time: 30, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '30'))   // 只保留最近 30 次构建
        disableConcurrentBuilds()                          // 禁止并发，避免部署冲突
    }

    environment {
        REGISTRY   = 'registry.example.com'
        IMAGE      = 'demo/web-app'
        IMAGE_TAG  = "${env.BUILD_NUMBER}-${env.GIT_COMMIT?.take(7)}"
    }

    stages {
        stage('1. 检出代码') {
            steps {
                checkout([$class: 'GitSCM',
                    branches: [[name: '*/main']],
                    userRemoteConfigs: [[
                        url: 'git@gitlab.example.com:demo/web-app.git',
                        credentialsId: 'gitlab-ssh-key'
                    ]]])
            }
        }

        stage('2. 依赖安装与构建') {
            steps {
                sh 'node -v && npm -v'
                sh 'npm ci --prefer-offline --no-audit'
                sh 'npm run build'
            }
        }

        stage('3. 单元测试与质量门禁') {
            steps {
                sh 'npm test -- --coverage'
            }
            post {
                always {
                    junit allowEmptyResults: true, testResults: 'reports/junit.xml'
                    archiveArtifacts artifacts: 'dist/**', fingerprint: true
                }
            }
        }

        stage('4. 构建并推送镜像') {
            when { branch 'main' }
            steps {
                sh '''
                    docker build -t $REGISTRY/$IMAGE:$IMAGE_TAG .
                    docker push  $REGISTRY/$IMAGE:$IMAGE_TAG
                '''
            }
        }

        stage('5. 部署到生产') {
            when { branch 'main' }
            steps {
                input message: '确认发布到生产环境？', ok: '发布'   // 人工审批卡点
                sh 'kubectl -n prod set image deploy/web-app web-app=$REGISTRY/$IMAGE:$IMAGE_TAG'
                sh 'kubectl -n prod rollout status deploy/web-app --timeout=180s'
            }
        }
    }

    post {
        success { echo '✅ 流水线执行成功' }
        failure { echo '❌ 流水线失败，请查看 Console Output' }
        always  { cleanWs() }                  // 清理工作区，防止磁盘膨胀
    }
}
注意：input 会阻塞构建并占用 executor，长时间等待建议改用 timeout 包裹，或放到独立的部署 Job 中。

6.5 触发方式与通知

触发方式配置位置说明
GitLab WebhookJob → 构建触发器 → Build when a change is pushed to GitLab最常用。GitLab 项目 Settings → Webhooks 填 http://jenkins/project/<JobName> 并生成 Secret Token。
定时构建Build periodicallyCron 语法，如 H 2 * * * 表示每天凌晨 2 点左右（H 为散列，避免惊群）。
SCM 轮询Poll SCMH/5 * * * * 每 5 分钟检查一次；无公网 IP 时的兜底方案。
远程 API 触发Trigger builds remotely带 Token 访问 URL，便于被外部系统（如发布平台）调用。
上游下游联动build job: 'xxx'在 Jenkinsfile 中触发另一个 Job，实现跨项目编排。

  • 权限：安装 Role-based Authorization Strategy 插件，按项目前缀给开发只读、给运维发布权限。

7GitLab CI/CD 操作手册

核心只需两步：装好 Runner，写好 .gitlab-ci.yml。

7.1 Runner 安装与注册

bash · Docker 方式部署 GitLab Runner
# 1. 启动 Runner 容器
docker run -d --name gitlab-runner --restart always \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest

# 2. 注册 Runner（token 从 GitLab 项目 → Settings → CI/CD → Runners 获取）
docker exec -it gitlab-runner gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.example.com/" \
  --token "glrt-xxxxxxxxxxxxxxxxxxxx" \
  --executor "docker" \
  --docker-image "node:20-alpine" \
  --description "docker-runner-01" \
  --tag-list "docker,node" \
  --run-untagged="false" \
  --locked="false"

# 3. 检查状态
docker exec -it gitlab-runner gitlab-runner list
docker exec -it gitlab-runner gitlab-runner verify
executor 怎么选： shell 直接跑在宿主机，简单但要自己管环境依赖； docker 每个 Job 独立容器，隔离性好，最常用； kubernetes 动态创建 Pod，适合大规模并发。
关键参数：--tag-list 给 Runner 打标签，Job 用 tags: 匹配；--run-untagged=false 表示只接带标签的 Job。

7.2 .gitlab-ci.yml 实战

.gitlab-ci.yml · 完整示例（Node 项目）
# 定义阶段执行顺序：build → test → package → deploy
stages:
  - build
  - test
  - package
  - deploy

# 全局变量
variables:
  IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  LATEST:    $CI_REGISTRY_IMAGE:latest

# 所有 Job 的默认配置
default:
  image: node:20-alpine
  tags:
    - docker
  before_script:
    - npm ci --prefer-offline --no-audit
  cache:
    key:
      files:
        - package-lock.json        # 锁文件变化才重建缓存
    paths:
      - node_modules/
    policy: pull

# ---------- 构建 ----------
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week              # 产物保留 1 周
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push              # 首个 Job 负责写缓存

# ---------- 测试 ----------
unit-test:
  stage: test
  script:
    - npm test -- --coverage
  coverage: '/All files[^|]*\|[^|]*\s+([\d\.]+)/'
  artifacts:
    when: always
    reports:
      junit: reports/junit.xml     # MR 页面直接展示测试结果

lint:
  stage: test
  script:
    - npm run lint
  allow_failure: true              # 暂不阻断流水线

# ---------- 打包镜像 ----------
package:image:
  stage: package
  image: docker:24
  services:
    - docker:24-dind               # Docker in Docker
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $IMAGE_TAG -t $LATEST .
    - docker push $IMAGE_TAG
    - docker push $LATEST
  rules:
    - if: '$CI_COMMIT_BRANCH == "main" || $CI_COMMIT_TAG'

# ---------- 部署预发 ----------
deploy:staging:
  stage: deploy
  image: alpine:3.19
  before_script: []
  script:
    - apk add --no-cache openssh-client
    - ssh -o StrictHostKeyChecking=no $SSH_USER@$STAGING_HOST "docker pull $IMAGE_TAG && docker restart web-app"
  environment:
    name: staging
    url: https://staging.example.com
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

# ---------- 部署生产（手动 + 仅打标签） ----------
deploy:production:
  stage: deploy
  image: alpine:3.19
  before_script: []
  script:
    - echo "部署 $IMAGE_TAG 到生产环境"
  environment:
    name: production
    url: https://www.example.com
  when: manual                      # 需人工点击触发
  rules:
    - if: '$CI_COMMIT_TAG'          # 仅在打 tag 时可用
常用预定义变量：CI_COMMIT_SHA（完整 commit）、CI_COMMIT_SHORT_SHA（短 SHA）、CI_COMMIT_BRANCH、CI_COMMIT_TAG、CI_PIPELINE_ID、CI_PROJECT_DIR、CI_REGISTRY_IMAGE、CI_JOB_TOKEN。

7.3 变量与密钥管理

  1. 进入项目 Settings → CI/CD → Variables → Add variable。
  2. 填写 Key / Value（如 SSH_PRIVATE_KEY、STAGING_HOST、KUBE_CONFIG）。
  3. 类型选 Variable（普通）或 File（内容是文件，如 kubeconfig，会落成临时文件路径）。
  4. 勾选 Protect variable：仅受保护分支 / 标签可见；勾选 Mask variable：日志中自动打码。
  5. 环境变量建议 Environment scope 按环境隔离（如 production 单独一套密钥）。
安全提醒：Masked 变量需满足格式要求（单行、无空格、至少 8 位）才能真正脱敏；含换行或特殊字符的密钥（如私钥）建议用 File 类型，避免被日志打印。

7.4 环境、发布与回滚

  • 查看部署记录：项目 → Operate → Environments，能看到每次部署的 commit、job 与耗时。
  • 一键回滚：在 Environments 页面找到历史部署记录，点击 Re-deploy 即可重跑当时的 Job。
  • 停止环境：配置 environment: on_stop: 指向一个 stop job，实现环境下线自动化。
  • 发布版本：配合 release: 关键字可自动创建 GitLab Release 与变更日志。
yaml · 带停止（回滚/下线）动作的环境
deploy:review:
  stage: deploy
  script: ./deploy.sh review
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://review-$CI_COMMIT_REF_SLUG.example.com
    on_stop: stop:review
  rules:
    - if: '$CI_MERGE_REQUEST_ID'

stop:review:
  stage: deploy
  script: ./deploy.sh stop
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
  when: manual
  rules:
    - if: '$CI_MERGE_REQUEST_ID'
      when: manual

7.5 模板复用与进阶

yaml · include 复用 + extends 继承 + 父子流水线
# 1) 引用模板（本地文件 / 其他项目 / 远程 URL）
include:
  - project: 'devops/ci-templates'
    ref: main
    file:
      - '/templates/node.yml'
      - '/templates/docker.yml'

# 2) 用 extends 继承公共配置，隐藏以 . 开头的模板 Job
.node_base:
  image: node:20-alpine
  tags: [docker]
  cache:
    key: node-modules
    paths: [node_modules/]

test:
  extends: .node_base
  stage: test
  script: npm test

# 3) 触发下游（父子）流水线 / 多项目编排
trigger:downstream:
  stage: deploy
  trigger:
    project: devops/infra
    branch: main
    strategy: depend      # depend 表示等待下游完成并继承其状态

# 4) 动态生成子流水线
generate:jobs:
  stage: build
  script: node ./ci/generate-pipeline.js > child-pipeline.yml
  artifacts:
    paths: [child-pipeline.yml]

run:child:
  stage: test
  trigger:
    include:
      - artifact: child-pipeline.yml
        job: generate:jobs

8最佳实践清单

流水线设计

  • 配置即代码：Jenkinsfile / .gitlab-ci.yml 必须入库并参与 Review。
  • 先快后慢：lint、单测放前面快速失败，重活（E2E、打包）放后面。
  • 构建产物只构建一次，测试与部署复用同一份产物/镜像，避免"每个环境重新编译"。
  • 镜像标签用 commit SHA，禁止用 latest 作为部署依据。
  • 所有部署都要能回滚，并在流水线里验证 rollout status。

性能与稳定

  • 缓存依赖（node_modules、.m2、Gradle），缓存 key 绑定锁文件。
  • 设置超时与丢弃策略，避免僵尸任务占满 executor。
  • 生产部署禁止并发（Jenkins disableConcurrentBuilds / GitLab resource_group）。
  • 敏感信息一律走凭据管理，禁止写进仓库或日志。
  • 固定工具镜像版本，避免上游镜像变更导致"昨天还好好的"。

质量门禁

  • 覆盖率、lint、安全扫描结果回传到 MR，作为合并前置条件。
  • 主干分支设为保护分支，禁止直接 push，必须走 MR + 流水线通过。
  • 分批灰度：pre → 小流量 → 全量，每步都有可观测指标。

可观测与协作

  • 失败通知直达责任人（企业微信 / 钉钉 / 邮件），附失败 Stage 与日志链接。
  • 关键指标：流水线成功率、平均时长、平均恢复时间（MTTR）。
  • 定期清理构建历史与旧镜像，控制存储成本。

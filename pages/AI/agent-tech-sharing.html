Agent 的两种形态，与前端如何优雅地流式渲染

从"按图施工"的工作流，到"自己决定下一步"的自主循环，再到 data:{type, content} 每一帧的落地渲染。

开场：先统一"什么叫 Agent"

一个最小可运行的 Agent，只需要三个零件：

  • 大脑（LLM）：负责理解、推理、决定下一步做什么。
  • 手脚（Tools）：函数、API、数据库、命令行，让模型能影响真实世界。
  • 记忆（Context / msg[]）：把"已经发生了什么"攒下来，喂给下一轮决策。

三者的组织方式不同，就长出了两种完全不同的 Agent 形态：工作流式（Workflow Agent）和自主式（Autonomous Agent）。下面一张图先建立直觉：

工作流式 Agent 像地铁：线路是提前修好的，站站停靠，到站下车。你大概率知道它下一步去哪。

自主 Agent 像打车：你只说目的地，司机根据实时路况自己选路，中途可能绕路、可能掉头，你无法预知完整路径——但你能到。

这个比喻基本贯穿全文。接下来三个部分，我们依次讲：它们是什么、它们怎么跑、前端怎么把过程展示出来。

1Agent 的两种类型

1.1 工作流式 Agent（Workflow Agent）

定义

由开发者在设计期把任务拆解成固定的节点与连线（通常是一个 DAG 有向无环图），运行时由编排引擎按图逐步执行。LLM 在其中只是"某个节点里的一个能力"，它可以做意图识别、信息抽取、文案生成，但它不决定流程走向——流程走向由开发者写死的边（edge）和条件表达式决定。

一句话概括：人在设计期做决策，机器在运行期做执行。

代表产品

低代码平台

  • Dify：Chatflow / Workflow 画布，拖拽式编排，国内落地最广
  • Coze（扣子）：Bot + 插件 + 工作流，偏 C 端与 Bot 分发
  • n8n / Zapier / Make：通用自动化，AI 节点只是其中一类节点
  • 腾讯云智能体开发平台、阿里云百炼：企业级工作流编排

代码框架

  • LangGraph：用 StateGraph 显式声明节点与边，可控性最强
  • LlamaIndex Workflows：事件驱动的显式编排
  • Spring AI Alibaba Graph：Java 侧的图编排方案
  • 各家 RPA（UiPath 等）加个 LLM 节点，本质也是这一类

典型应用场景

场景为什么适合工作流示例流程
企业客服 / FAQ 问答 路径可穷举：分类→检索→回答→兜底转人工。SLA 和话术都需要稳定可控 意图分类 → 知识库检索 → 相关性判别 → 生成答案 → 命中不了则转人工
表单/单据处理 OCR → 抽取 → 校验 → 入库，每一步都有明确的输入输出与失败重试策略 上传发票 → OCR → 字段抽取 → 规则校验 → 写 ERP → 结果通知
营销文案批量生成 模板固定、量大、要求格式一致，成本敏感 读取商品表 → 并行调用 LLM → 合规审核 → 落库
数据报表 / ETL + 解读 取数逻辑必须先验证正确性，不能让模型"自由发挥"写 SQL 定时触发 → 固定 SQL 取数 → 生成图表 → LLM 写解读
有合规要求的业务流程 需要留痕、可审计、可复现，审批节点必须人工介入 材料初审 → 规则引擎 → 人工复核 → 归档
选型直觉 当你能用一张流程图把需求画完整、且这张图半年内不会大改时——用工作流。

1.2 自主 Agent（Autonomous Agent）

定义

开发者只提供目标、可用工具集和约束（系统提示词、最大轮次、权限边界），由 LLM 在运行期自主决定调用什么工具、调用几次、什么时候停。没有预先画好的图，路径是推理出来的，不是设计出来的。

一句话概括：人在设计期只定边界，机器在运行期既做决策也做执行。

它的基本形态就是一个循环（下一节会展开）：维护一个 msg[] → 组装上下文 → 调 LLM → 模型说"我要调工具" → 执行工具 → 结果写回 msg[] → 再调 LLM → …… → 直到模型认为可以收工。

代表产品

编码类

  • Claude Code / Cursor Agent / CodeBuddy / 通义灵码：读写文件、跑命令、跑测试，自我纠错
  • Devin、OpenAI Codex：更彻底的异步自主执行

通用类

  • OpenAI Deep Research / Operator：自主检索、自主操作浏览器
  • Manus、AutoGPT、OpenHands：通用任务自主规划
  • 各家"深度研究"模式：多轮检索 + 交叉验证

典型应用场景

场景为什么必须自主典型表现
代码编写与重构 改一个 bug 要先读哪些文件、读多少层，事前无法穷举 自己 grep、读文件、改代码、跑测试、看报错、再改，循环十几轮
深度研究与调研 搜到什么才知道下一步该搜什么，路径依赖中间结果 搜索 → 读页面 → 发现新线索 → 再搜索 → 交叉验证 → 成文
数据分析探索 看到数据分布才知道该清洗什么、该画什么图 执行 Python → 看图 → 觉得不对 → 换维度重跑
运维排障 / 根因定位 故障现场千变万化，无法预先编排排查树 看日志 → 查监控 → 登机器 → 缩小范围 → 定位
开放域长任务 需求本身模糊，需要在过程中逐步澄清 先出计划 → 中途反问用户 → 调整方向 → 继续
注意代价 自主 Agent 的每一次"聪明"，都是用 token 成本、延迟、结果不确定性换来的。同一个问题跑两次，路径可能完全不同。

1.3 优劣对比与适用边界

维度 工作流式 Agent 自主 Agent

确定性与可测 易测，可对单节点做单测与回归 难测，只能做端到端评估与轨迹回放

选工作流的信号 稳定优先

  • 业务流程已经被标准化，或者有明确的 SOP
  • 对成功率、延迟、成本有硬指标
  • 涉及合规、审计、责任划分
  • 调用量大，成本敏感
  • 需要非技术同学参与维护

选自主 Agent 的信号 能力优先

  • 任务无法穷举路径，边走边看
  • 用户是专业人士，能容忍过程、能纠偏
  • 单次任务价值高，成本不敏感
  • 允许异步、允许人工介入确认
  • 环境可回滚（沙箱、容器、版本控制）
别把它当二选一 现实里绝大多数产品是混合的：外层用工作流保证主干可控（鉴权、分类、审计、兜底），内层在某些节点里嵌一个自主 Agent 去啃硬骨头（写作、检索、编码）。业界常说的 "Agentic Workflow" 指的就是这种在图的某个节点里跑循环的形态。判断标准只有一个：这一步的决策，你敢不敢交给模型。

2两种 Agent 的工作方式

2.1 工作流式：把图画好，按图施工

工作流式的执行过程可以理解成：拓扑排序 + 逐个执行节点 + 沿条件边跳转。每个节点有明确的输入（上游状态）、处理逻辑和输出（写入共享状态）。引擎不关心节点内部是调 LLM、查库还是跑代码，它只负责"该跑谁了"。

用伪代码看会更直接——图是数据，不是控制流：

// 工作流式 Agent：图已经画好，引擎只负责"按图施工"
const graph = defineGraph({
  nodes: {
    classify:   { type: 'llm',  prompt: '判断用户意图', output: ['faq', 'order'] },
    retrieve:   { type: 'tool', name: 'vector_search' },
    queryOrder: { type: 'tool', name: 'query_order'  },
    merge:      { type: 'code', fn: (ctx) => ({ ...ctx.retrieve, ...ctx.queryOrder }) },
    answer:     { type: 'llm',  prompt: '基于资料回答用户问题' },
  },
  edges: [
    ['__start__', 'classify'],
    // 走哪条分支，是开发者写的函数，不是模型决定的
    ['classify',   'retrieve',   { when: ctx => ctx.classify === 'faq'   }],
    ['classify',   'queryOrder', { when: ctx => ctx.classify === 'order' }],
    ['retrieve',   'merge'],
    ['queryOrder', 'merge'],
    ['merge',      'answer'],
    ['answer',     '__end__'],
  ],
});

const result = await graph.run({ question: '我的订单到哪了' });
// 实际路径：classify → queryOrder → merge → answer（retrieve 根本不会执行）
// 整条路径可预测、可追踪、可回放、可对单节点做单测
关键特征 LLM 调用次数是常数级的（图里有几个 LLM 节点就调几次），所以成本和延迟都算得出来。这是它能进生产、能承诺 SLA 的根本原因。

动手点一点：工作流是怎么"按图施工"的

点「下一步」，看引擎如何逐个点亮节点、把结果写进共享 State，以及没有命中的分支会被整体跳过。这个例子里用户问"我的订单到哪了"。

对照自主 Agent 看这张图 注意第 4 步：知识库检索与代码执行器两个节点是"死"的——无论模型多想调用，图上没有通往它们的边，它们就不会执行。这正是工作流"可控"的来源，也是它"不灵活"的代价。

2.2 自主式：一个循环，模型自己决定何时停

自主 Agent 没有图。它只有一个循环，以及一个不断变长的消息数组 msg[]。流程如下：

  1. 初始化：把用户输入塞进 msg[]，同时准备好工具清单（每个工具的 name / 参数 JSON Schema / 描述）。
  2. 组装上下文：系统提示词 + msg[] 全量历史 + 工具定义 + 可选的长期记忆/RAG 片段，拼成一次 LLM 请求的 payload。
  3. 调用 LLM API：注意这里是让模型输出"下一步动作"，而不是输出最终答案。模型可以回一段普通文本，也可以回一个 tool_calls 结构。
  4. 模型判断：
    • 如果返回 tool_calls → 说明它想调工具，进入第 5 步；
    • 如果只返回文本 → 说明它认为可以收工了，循环结束，输出这段文本。
  5. 执行工具：解析出工具名和参数，在本地/远端执行（查库、调 API、跑命令、读文件……）。
  6. 结果写回 msg[]：以 { role: 'tool', tool_call_id, content } 的身份追加进去。
  7. 回到第 2 步，带着更长的上下文再问一次模型。直到模型主动结束，或触发兜底条件（最大轮次 / 超时 / token 上限）。
三个容易踩的坑 ① 终止条件是模型说了算，所以必须有 MAX_TURNS 硬兜底，否则可能出现"调工具→结果不满意→再调工具"的死循环烧钱。
② msg[] 只增不减，上下文会线性膨胀，需要压缩/摘要/裁剪策略（尤其是工具返回大 JSON 时）。
③ 工具返回的错误也要写回 msg[]——报错信息是给模型看的，它往往能自己换个参数重试。

对应到代码，核心其实只有十几行：

async function agentLoop(userInput) {
  // 记忆：整个循环唯一的可变状态
  const msg   = [{ role: 'user', content: userInput }];
  const tools = getToolSchemas();   // 工具的 name / description / JSON Schema

  for (let turn = 0; turn < MAX_TURNS; turn++) {

    // ① 组装上下文：系统提示 + 历史消息 + 可用工具 + 记忆
    const payload = buildContext({ system: SYSTEM_PROMPT, msg, tools });

    // ② 调 LLM：让模型自己决定下一步（而不是给最终答案）
    const res = await llm.chat(payload, { stream: true });

    // ③ 把"这一轮模型的决定"写回消息数组
    msg.push(res.message);   // 可能是纯文本，也可能带 tool_calls

    // ④ 终止条件：模型不再要调工具 —— 由 LLM 决定结束
    if (!res.message.tool_calls) return res.message.content;

    // ⑤ 执行工具，结果以 role:'tool' 写回 —— 然后循环继续
    for (const call of res.message.tool_calls) {
      let output;
      try {
        output = await runTool(call.name, call.args);
      } catch (e) {
        output = `执行失败：${e.message}`;  // 报错也喂给模型，让它自己重试
      }
      msg.push({ role: 'tool', tool_call_id: call.id, content: output });
    }
  }
  throw new Error('超出最大轮次，强制结束');
}

注意第 ⑤ 步里的注释 报错也喂给模型，让它自己重试——这是自主 Agent 与"传统程序"最大的思维差异：错误不再是异常，而是给模型的反馈。模型看到"文件不存在"，会自己换个路径再试；看到"参数格式不对"，会自己修正参数。

动手点一点：Agent Loop 转起来的样子

点「下一步」，一次走一个阶段。重点看两件事：右侧 msg[] 每转一圈就变长一截（上下文只增不减），以及循环什么时候停——不是走完固定步数，而是某一轮模型不再返回 tool_calls。

    把两个演示放在一起看 工作流那边 7 步就结束了，且路径在图里已经写死；自主 Agent 这里转了几圈取决于模型——同一个问题换个模型、换个 temperature，可能 2 轮就收工，也可能转 8 轮。代价是 msg[] 线性膨胀：第 3 轮时上下文已经是第 1 轮的 5 倍，这也是为什么长任务必须做摘要压缩。

    2.3 本质差异一句话

    工作流式自主式
    谁决定下一步开发者写的图与条件LLM 的推理结果
    状态在哪图的共享 State（结构化、可序列化）msg[] 消息数组（半结构化、自然语言）
    谁决定结束走到 __end__ 节点LLM 不再返回 tool_calls
    循环次数0（DAG 无环）不固定，需上限兜底
    类比编译期确定的调用链while 循环 + 动态派发

    如果只用一句话：工作流式是"人编排流程，LLM 填空"；自主式是"LLM 编排流程，人定边界"。

    3前端流式输出：把 Agent 的"过程"渲染出来

    3.1 为什么必须流式

    自主 Agent 跑一轮可能要几十秒甚至几分钟：中间要调好几次工具、每次都要等模型推理。如果做成"转圈圈 → 一次性返回全部结果"，体验上是灾难：

    • 用户不知道它在干什么，3 秒没反馈就想刷新页面；
    • 出错时前面的工作全部白费，没有中间态可看；
    • 自主 Agent 的核心卖点就是"过程透明"（它在读哪个文件、跑了什么命令），藏起来就失去了意义。

    所以业界的共识做法是：Agent 服务层把 LLM 的输出用 SSE 流式吐给前端，前端按事件类型增量渲染。

    3.2 协议约定与时序

    我们约定响应头为 Content-Type: text/event-stream，每一帧是一个 SSE 事件，data 里是一个 JSON 对象，且只约定两个顶层字段：

    data:{"type":"tool_call","content":{"id":"c1","name":"query_order","args":{"orderId":"A10086"}}}

// 字段约定
// type    : string —— 事件类型，前端据此决定怎么渲染
// content : any    —— 载荷，结构由 type 决定（文本就是字符串，结构化事件就是对象）
// 流结束：服务端发 data:[DONE] 后关闭连接
    为什么用 {type, content} 这种极简结构 ① 前端只需要一个 switch(type)，新增事件类型时不改解析层，符合开闭原则；
    ② 与后端/模型侧解耦——同一个 tool_result 事件，今天来自 GPT、明天来自自研模型，前端代码不用动；
    ③ 天然支持扩展：想加"引用来源"、"思维链"、"子 Agent"，只是多一个 type，协议不用升级。

    3.3 事件类型清单

    下面这张表可以直接当作前后端联调的契约。content 的结构按 type 走，前端只认 type。

    type content 结构 前端应该做什么
    text / delta string 正文增量，追加到当前 Markdown 块的尾部，边收边渲染
    thinking string 思考/推理过程，放进可折叠区块，灰色小字，默认收起
    plan { steps: string[] } 渲染任务清单，随进度逐条打勾
    tool_call { id, name, args } 工具可视化：新建一张工具卡片，显示图标+名称+参数，状态 = 执行中（转圈）
    tool_result { id, name, output } 用 id 找到那张卡片，卡片状态置为成功，内容区展开渲染 output
    tool_error { id, name, message } 卡片置为失败（红色），展示错误信息，可选提供"重试"
    sub_agent_start { id, parentId, task } 嵌套缩进一张子 Agent 容器卡片，标题显示任务描述
    sub_agent_result { id, result } 子 Agent 容器收起为摘要，可点开查看完整过程
    human_in_loop { id, title, options[] } 人类确认：弹出确认 UI，阻塞当前流，用户选择后回调服务端
    error { code, message } 全局错误提示条，停止渲染，保留已生成内容
    final / done { content, usage } 收尾：解除 loading，显示 token 消耗，开放复制/重新生成

    3.4 前端解析与分发

    第一步：把字节流切成事件

    注意 EventSource 只支持 GET，Agent 场景一般需要 POST（要传 msg[]、工具开关、会话配置），所以更常用 fetch + ReadableStream 手动解析。关键点是处理"半包"——一个 chunk 里可能只有半个 JSON。

    // 把 SSE 字节流解析成一个个 { type, content } 事件
async function* sseIterator(res) {
  const reader  = res.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });

    // SSE 以空行分隔事件；pop() 把最后一段可能不完整的留到下一轮
    const parts = buffer.split('\n\n');
    buffer = parts.pop() ?? '';

    for (const part of parts) {
      const line = part.split('\n').find(l => l.startsWith('data:'));
      if (!line) continue;

      const raw = line.slice(5).trim();
      if (raw === '[DONE]') return;

      try {
        yield JSON.parse(raw);   // { type, content }
      } catch {
        // 单帧解析失败别让整条流挂掉，记日志继续
        console.warn('SSE 帧解析失败', raw);
      }
    }
  }
}

    第二步：按 type 分发到状态机

    建议把"收到事件 → 更新 UI"做成一个纯函数 reducer，好处是可测、可回放、可时间旅行调试（把事件流存下来就能复现任意一次会话界面）。

    function reducer(state, ev) {
  switch (ev.type) {
    case 'text':              return appendText(state, ev.content);
    case 'thinking':          return appendThinking(state, ev.content);
    case 'tool_call':          return upsertTool(state, ev.content, 'running');
    case 'tool_result':        return upsertTool(state, ev.content, 'success');
    case 'tool_error':         return upsertTool(state, ev.content, 'error');
    case 'sub_agent_start':    return openSubAgent(state, ev.content);
    case 'sub_agent_result':   return closeSubAgent(state, ev.content);
    case 'human_in_loop':      return { ...state, pendingConfirm: ev.content };
    case 'final':              return { ...state, finished: true, usage: ev.content.usage };
    default:                    return state;   // 未知 type 直接忽略，保证向后兼容
  }
}

// 消费
for await (const ev of sseIterator(res)) {
  setState(s => reducer(s, ev));
  if (ev.type === 'human_in_loop') await handleConfirm(ev.content);
}
    向后兼容的小技巧 default 分支一定要"静默忽略"而不是抛错。这样后端新增事件类型时，老版本前端不会白屏，只是暂时不展示而已。

    3.5 按 type 渲染不同样式：从协议到 UI 的映射层

    上一节解决了"怎么把事件收上来"，这一节解决"收到的事件到底长什么样"。很多团队一开始会写成一大坨 if (type === 'tool_call') { ... } else if (...) { ... }，很快就会失控。推荐的做法是三层解耦：

    事件流（SSE）→ Block 数据模型（可渲染单元）→ 组件与样式映射表（渲染层）

    事件协议变了，只改第一层；新增一个视觉类型，只改第三层的一张表。中间的数据模型保持稳定。

    第一层：把"事件流"折叠成 Block 列表

    事件是流式的、零散的、不可寻址的（一个 token 就是一个事件）；而 UI 需要的是有序的、可寻址的、可更新的列表。所以中间必须有归并：

    // Block = 渲染的最小单位。注意：kind 来自 type，但不是一一对应
//（tool_call / tool_result / tool_error 三个 type 归并为同一个 tool Block）
type Block =
  | { kind:'text',     id, text:string,  streaming:boolean }
  | { kind:'thinking', id, text:string,  folded:boolean }
  | { kind:'tool',     id, label, name, args, output?,
                       status:'running'|'success'|'error' }
  | { kind:'subAgent', id, parentId, task, children:Block[],
                       status:'running'|'success'|'error', folded:boolean }
  | { kind:'confirm',  id, title, options:string[], choice? }
  | { kind:'error',    id, message, retryable:boolean };

    归并只有两条核心规则，记住就不会乱：

    • 连续的 text 追加到同一个 Block——否则每个 token 都会变成一个新的 <p>，DOM 节点爆炸。
    • tool_call / tool_result / tool_error 按 id upsert 同一个 Block，只改它的 status 和 output，不新建卡片。

    第二层：kind → 组件映射表（Registry）

    别写 switch...case 输出 JSX，用注册表。新增一个类型时只改一行，符合开闭原则：

    // type(kind) → 组件：新增视觉类型，只改这一张表
const RENDERERS = {
  text:     TextBlock,       // 正文       —— 无框，Markdown 渲染
  thinking: ThinkingBlock,   // 思考过程   —— 灰底折叠块
  tool:     ToolCard,        // 工具调用   —— 蓝色卡片，三态
  subAgent: SubAgentBlock,   // 子 Agent   —— 紫色嵌套容器
  confirm:  ConfirmBar,      // 人类确认   —— 橙色横条 + 按钮
  error:    ErrorBar,        // 错误       —— 红色横条 + 重试
};

function BlockList({ blocks }) {
  return blocks.map(b => {
    const Comp = RENDERERS[b.kind] ?? FallbackBlock;  // 未知类型兜底，绝不白屏
    return <Comp key={b.id} block={b} />;
  });
}

    第三层：样式映射 —— tone × layout × status 三维正交

    这是"渲染不同样式"的关键：不要把样式写死在每个组件里，而是抽成三个正交维度，用一张表描述：

    • tone（色调）：由 kind 决定——体现"这是什么性质的信息"（中性 / 次要 / 主操作 / 子任务 / 警告 / 危险）。
    • layout（形态）：由 kind 决定——体现"信息量大小"（纯文本 / 引用块 / 卡片 / 横条 / 嵌套容器）。
    • status（状态）：由运行进度决定——体现"现在进行到哪一步"（执行中 / 成功 / 失败），与 kind 正交：同一个 ToolCard 会有三种状态。
    // 一张表决定"长什么样"：kind → { 图标, 色调, 形态 }
const VISUAL = {
  text:     { icon: null,  tone: 'plain',   layout: 'full'  },
  thinking: { icon: '💭', tone: 'muted',   layout: 'quote' },
  tool:     { icon: '🔧', tone: 'accent',  layout: 'card'  },
  subAgent: { icon: '🤖', tone: 'purple',  layout: 'nest'  },
  confirm:  { icon: '⚠️', tone: 'warning', layout: 'bar'   },
  error:    { icon: '⛔', tone: 'danger',  layout: 'bar'   },
};

// 组件里只做一件事：把三个维度拼成 className
function cx(kind, status) {
  const v = VISUAL[kind];
  return [
    'blk',
    `blk--${v.tone}`,          // 色调：配色方案
    `blk--${v.layout}`,        // 形态：DOM 结构
    status && `is-${status}`,    // 状态：running / success / error
  ].filter(Boolean).join(' ');
}

// 例：cx('tool','running') → "blk blk--accent blk--card is-running"
    为什么值得抽这一层 ① 设计师改配色时，你只改 CSS 里的 6 个 tone 类，不用碰任何组件；
    ② 想做暗色主题，只需再写一套 tone 变量；
    ③ 新增事件类型时，登记表 + 视觉表各加一行即可，渲染主流程零改动。

  return (

      )}
    </div>
  );

      3.6 五类事件的渲染要点

      ① 工具可视化（tool_call / tool_result / tool_error）

      结构和状态怎么映射在 3.5 已经讲过（三个 type 归并成一张卡片，用 id upsert、status 驱动三态）。这里补充交互层面最容易翻车的几点：

      • 输出必须截断：工具返回的 JSON 动辄几万字符，卡片默认只显示前 12 行 + "查看完整输出"。否则一次查询能把页面撑到几万像素高。
      • 同类型工具连续调用要合并：连读 10 个文件时，折叠成"已读取 10 个文件"，点击才展开。否则界面被刷屏，用户找不到重点。
      • 耗时工具要显示计时器：超过 3 秒还在转圈，用户会以为卡死。在 blk__aside 里放一个实时秒表。
      • 重试必须"原地重试"：点击重试后更新原卡片的 status，不要新建一张卡片，否则会话里堆满同名的失败记录。
      • 参数要"人话化"：不要直接把 {"path":"/src/a.ts"} 甩给用户，用 3.5 那张 TOOL_META 表映射成"正在读取文件 a.ts"。

      ② 正文文本（text）

      • 增量追加，配合 markdown-it / marked 流式渲染；注意未闭合的代码块要在收尾时补上 ```。
      • 高频 token 会导致每帧重排卡顿，见下一节的节流方案。

      ③ 子 Agent 结果（sub_agent_*）

      • 用 parentId 维护树形结构（对应 3.5 里的 subAgent 嵌套块），并限制嵌套最多 2~3 层——再深缩进就没地方了，改成"点击展开新面板"。
      • 子 Agent 内部会有自己的 tool_call，需要按 parentId 归属，否则会和主 Agent 的工具卡片混在一起。
      • 子 Agent 结束后默认折叠成一行摘要，点击才展开完整轨迹——否则长任务界面会崩溃。

      ④ 人类确认（human_in_loop）

      这是最容易被做错的一块，因为它是唯一需要前端"反向写回"的事件。

      • 服务端推 human_in_loop 后，保持 SSE 连接打开但不再推业务事件（或明确暂停），前端渲染确认 UI。
      • 用户点击后，前端调 POST /api/session/:id/resume，带上 { callId, decision }，服务端据此把结果写回 msg[]，从断点继续循环。
      • 要有超时策略：用户一直不点，服务端不能无限等，超时按默认选项（通常是"取消"）继续或直接终止。
      • 敏感操作（删文件、发邮件、付款）必须走这条链路，并在 UI 上高亮参数，让用户看清到底要执行什么。
      async function handleConfirm({ id, title, options = ['确认', '取消'] }) {
  const choice = await confirmDialog({ title, options });   // 返回用户选择

  await fetch(`/api/session/${sessionId}/resume`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ callId: id, decision: choice }),
  });
  // 之后服务端会继续在同一个流里往下推事件
}

      ⑤ 结束与错误（final / error）

      • final：解除 loading、显示 token 消耗和耗时、开放"复制 / 重新生成 / 点赞点踩"。
      • error：保留已生成的内容，只在顶部加错误条。用户最痛恨"跑了 2 分钟一行字都没了"。
      • 无论哪种，都要在 finally 里 reader.cancel() / controller.abort()，避免连接泄漏。

      3.7 工程化细节（这些才是真正花时间的地方）

      渲染节流：别让每帧都触发重排

      流式场景下每秒可能来几十个 token，每个都 setState 会让 React 疯狂重渲染。用 requestAnimationFrame 合并：

      let pending = false;
function scheduleRender() {
  if (pending) return;
  pending = true;
  requestAnimationFrame(() => { pending = false; flushToDOM(); });
}
// 每帧最多渲染一次，60fps 下人眼照样觉得是"实时打字"

      断线重连：Last-Event-ID

      • 服务端给每个事件带 id: 字段，客户端断线后用 Last-Event-ID 请求头续传。
      • 或者让 final 事件里带完整内容，重连时先拉全量快照再增量追加——实现更简单，推荐小团队这么做。

      其他 checklist

      • 心跳保活：每 15s 推一帧 SSE 注释（: ping）或空业务事件，防止代理层（Nginx、网关）掐断空闲连接。
      • Nginx 配置：proxy_buffering off; proxy_read_timeout 600s; chunked_transfer_encoding on;——这三个漏一个就会出现"本地流式正常，上线后一次性返回"。
      • 禁用压缩：部分网关开了 gzip 会缓冲整个响应，SSE 需要对该路由关闭（或设置 X-Accel-Buffering: no）。
      • 主动中断：用 AbortController 实现"停止生成"，同时通知服务端及时停掉 LLM 调用，省 token。
      • XSS 防护：工具输出和 LLM 内容都不可信，Markdown 渲染必须走 DOMPurify sanitize，尤其是 tool_result 里的 HTML。
      • 自动滚动：仅当用户处于底部时才自动滚，用户手动上滑后要停住（很多产品在这里体验翻车）。
      • 移动端：SSE 在部分移动端浏览器后台会被挂起，需要 visibilitychange 时做状态校验与重连。
      • 可观测性：前端把收到的事件流打点上报（type、时间戳、content 长度），出问题时能还原"用户到底看到了什么"。

      4小结

      三句话总结

      1. 两种形态：工作流式是"人编排流程，LLM 填空"，可控省钱但怕变化；自主式是"LLM 编排流程，人定边界"，能啃硬骨头但成本高、结果不确定。生产环境多是混合形态。
      2. 两种工作方式：工作流是按 DAG 逐步执行、走到终点节点结束；自主 Agent 是一个循环——组装上下文 → 调 LLM → LLM 决定是否调 tool → 执行 → 结果写回 msg[] → 再问 LLM，直到 LLM 自己决定结束。
      3. 前端流式：服务层把过程拆成 data:{type, content} 的 SSE 帧，前端只做一件事——按 type 分发到对应的渲染逻辑，工具卡片用 id 做 upsert、人类确认要反向写回、高频更新用 rAF 节流。

      最后留一个问题给大家思考：当 Agent 的决策路径不再由人类编写，"前端展示过程"这件事就从"锦上添花"变成了"信任基础设施"——用户只有看得见它在干什么，才敢把重要的事交给它。这也是为什么流式渲染在 Agent 时代不再是优化项，而是必选项。
